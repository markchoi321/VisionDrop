# VD-D1 密集彩色 L1 接收端（实验）

规约见 [protocol/dense/DENSE.md](../../../protocol/dense/DENSE.md)，
行为参照 `protocol/dense/dense_refimpl.py` 的图像解码器。

## 结构

| 文件 | 内容 |
|---|---|
| `vd_dense_core.h` / `.c` | 纯 C99 解码核心，零依赖。定位、几何校正、采样、定标判决、RS errata |
| `DenseDecoder.swift` | Swift 封装：CVPixelBuffer / RGB24 到 C API 的零拷贝桥接与跟踪状态 |
| `DenseCameraScanner.swift` | 相机采集管线：BGRA 输出、AE/AWB 锁定（对焦保持自动）、串行解码队列 |
| `DenseScannerView.swift` | 扫描界面：档位选择、锁定状态、帧率读数 |
| `QrBinary-Bridging-Header.h` | 桥接头 |

入口在主界面的「密集 8 色扫描（实验）」按钮，档位默认**自动判别**。

### 档位自动判别（真机踩坑记录）

首次真机测试的表现是「定位图形找得到，但头部校验失败」，原因是发送端用
128 格而接收端固定在 96 格。定位图形只是四个角，**在图像空间里跟 N 无关**，
所以照样能找到；但 N 一错，单应性就整体错尺度，格心全数偏掉。

符号本身不携带 N（格式短板），因此解码器改为逐个候选档位试探：
只采样定标条（32 格）与头部（120 格）就能判定，不做全符号采样，
单个候选约 1 ms，判出后随跟踪锁复用。头部有魔数 + 版本 + CRC8 共 20 位校验，
错误档位蒙对的概率约百万分之一。

`vdd_decode` 传 `VDD_GRID_AUTO`(0) 即自动；传具体档位仍可固定，用于排查。

解出的字节是标准 L2 帧，交给现有 `FrameParser` 与解码器，L2–L5 不感知物理层。

## 线程安全

解码是纯函数式的（输入图像 → 输出字节），但**文件里所有可变的 `static` 缓冲
都是共享的**，两个线程同时解码就会互相踩。App 里解码跑在单条串行队列上，
所以一直没暴露；Swift Testing 默认并行跑用例，两个解码用例撞上就随机失败——
表现为「没改代码，测试却红了」，极难归因。现在的处置：

| 缓冲 | 处置 |
|---|---|
| `gf_exp` / `gf_log` / `gf_ready`、`rs_encode` 的生成多项式 | `_Thread_local`（每线程几百字节） |
| `find_finders` 的 `local_thresh`（约 48 KB） | 改堆分配，各出口释放 |
| `lt_build` 的块统计临时数组 | 并入 `local_thresh` 结构体 |
| `calib_thresholds` 的采样缓冲 | 改栈上，尺寸按 `CALIB_MAX_SAMPLES` 收到实际用量 |
| `vdd_net_capacity` 的 64 KB 索引表 | 换成只计数的 `free_cells_count` |

新增依赖解码核心的并行测试时，这条要一起想到。

## 为什么是 C

解码是确定性数值计算，没有 ML 推理。纯 C 便于编译器自动向量化（NEON），
单次 malloc 工作区，无 ARC 与桥接开销；热点若需进一步优化可直接手写 intrinsics
或换 Metal，接口不变。

实测（Apple Silicon，`-Os -flto`，单线程，不含相机采集）：

| 档位 | 图像 | 冷启动（全图搜索） | 跟踪态（四角小窗） |
|---|---|---|---|
| N=64 | 544² | 0.46 ms | 0.20 ms |
| N=96 | 800² | 1.09 ms | 0.51 ms |
| N=128 | 1056² | 2.17 ms | 1.02 ms |

30fps 的每帧预算是 33 ms，余量充足；GPU 路径暂无必要。

## 关键实现点

- **亮度域游程扫描**找定位图形（1:1:3:1:1），只读 RGB 的亮度组合，不做全帧色彩转换。
- **跟踪锁**：`vdd_lock` 保存四角坐标与已标定的形状参数，下一帧只在四角附近
  小窗重扫；失锁（头部 CRC 失败或找不到定位图形）自动清锁并回退全图搜索。
- **RS errata 解码**：采样值贴近判决阈值的格标记为擦除喂给 RS。
  擦除的纠错代价是错误的一半，32 奇偶理论可纠 32 擦除 / 16 错误，
  但实际封顶在 24 擦除（`RS_ERAS_MAX`）——留 8 个校验符号做独立复验，
  否则擦除吃满时复验恒真、会报伪成功。擦除若误导致失败，退回纯错误模式重试一次。
- **定标条**决定每通道阈值与半间隔；半间隔过小（< 8）判定定标失效，直接丢帧。

## 现场诊断

界面右上角菜单 →「导出诊断帧」把下一帧相机原始像素存成 24 位 BMP 并调起分享。
**该 BMP 可直接喂给 C 侧 harness 复现**，无需重建现场：

```bash
clang -O2 -std=c99 -o vddh protocol/dense/harness.c receiver/QrBinary/DenseL1/vd_dense_core.c -lm
./vddh -r 5 protocol/dense/golden/*.bmp        # 金图像回归
./vddh -l testdata/vdd-diag/fail*.bmp          # -l 跨帧复用跟踪锁，模拟连续取景
```

harness 每帧打印解码结果、分阶段耗时与 RS 观测量。**优化解码器时速度与准确性
必须一起看**——本仓库已经有两次「明显更快」的改动实测把原本整帧解出的真机
照片打成 0 块通过，见下面「试过但退回的优化」。

界面底部常驻一行标定读数。**成功时**显示「档位 / 每格像素 / 弓曲 / 头部分歧」，
**失败时**显示走得最远那个候选档位的「档位 / 每格像素 / 三通道对比度」——
判断是几何没对上（对比度接近 0）还是真的对比度不足（几何对但数值偏低），
全靠这几个数。

失败原因按走得最远的候选报告，而不是最后一个候选：`CALIB` 说明几何就没对上，
`HEADER` 说明几何与定标都过了、只是校验没通过。

## 二值化：局部自适应阈值

定位图形的游程扫描用分块局部阈值（思路同 ZXing 的 HybridBinarizer），
不用全局阈值——暗环境里拍一块亮屏时，全局均值会被大片背景拉偏，
二值化随之失准，1:1:3:1:1 的比例就对不上了。

但**格值判决不用阈值**：真机实测证明三通道独立阈值判不了八色（相机对屏幕
基色有强串扰，单通道是三峰分布），现按定标条实测的八色调色板做三维最近邻，
详见 `vd_dense_core.c` 中 `PAL_MIN_SEP` 上方的注释。四条定标条正好在四角，
按位置双线性插值顺带补偿光照梯度与白平衡不均。

二均值阈值仍然保留：一是定标条在极低像素密度下会被相邻格污染、八色挤到一起，
此时退回阈值判决；二是它给出的对比度读数是现场诊断的主要依据。

### 与 JAB Code 的取舍对照

[jabcode](https://github.com/jabcode/jabcode) 的判决在 `decoder.c` 的
`decodeModuleHD` / `getNearestPalette`，思路与这里同构（符号自带每角一套调色板、
三维最近邻），但两处细节不同。**两处我们都实测过，都保留了自己的做法**：

| 判决方案 | c128_1 | c128_2 | c128_3 | c128_4 |
|---|---|---|---|---|
| **绝对 RGB + 四角双线性**（本实现） | 22/22 纠 9.1 | 22/22 纠 9.6 | 22/22 纠 0 | 22/22 纠 0.5 |
| 绝对 RGB + 硬选最近角 | 21/22 纠 10.9 ✗ | 21/22 纠 12.0 ✗ | 22/22 纠 0.5 | 22/22 纠 1.9 |
| 归一化色度 + 双线性（JAB 判决） | **0/22** ✗ | **0/22** ✗ | 22/22 纠 0 | 22/22 纠 0 |

（✗ = 整帧解不出；「纠」为通过块平均纠正字节数，越小越好）

1. **选哪套调色板**：JAB 按 Voronoi 硬选最近的那一角，我们做四角双线性插值。
   实测插值在四张上一致更好——光照梯度是连续的，硬划分在分界线上会突变。
2. **归一化**：JAB 先按最大通道归一化，只比色度、丢掉亮度，因此还必须把黑单独
   用阈值挑出来、并对 0/7 用原始 RGB 和消歧（黑与白归一化后都是 (1,1,1)）。
   这套在两张较暗的照片上直接崩掉：近黑格除以一个很小的 max，噪声被成倍放大。
   我们保留绝对 RGB 距离——光照梯度已经由插值吸收，亮度轴反而是有用的判别信息。

JAB 的取值在它的场景（打印件、光照更均匀、色数可变到 4/8）大概率是对的；
这里是屏摄、亮度波动大但色彩响应固定，结论就反过来了。取样方式两边一致：
单一全局透视变换 + 格内邻域平均（`sampleSymbol` / `warpPoints`）。

## 真机实测结论（2026-08-04，6 张 4032×3024 照片，N=96 与 N=128）

**现状：六张全部整帧解出并通过 L2 CRC**，六帧的 sessionId 完全一致
（同一次发送），同一帧拍的两张解出的字节逐字节相同。
`testdata/` 下的原图即回归样本，`DenseRealShotTests` 在模拟器上直接读源码树里的
原始 HEIC/JPEG（不入 bundle，见该文件注释）。

一路修掉六个真 bug，按发现顺序：

1. **缺最小模块尺寸门限**。比例容差是 `u×0.75`，`u` 很小时容差降到亚像素级，
   任何噪点都能通过 1:1:3:1:1 检验。实测检出 128 组候选**全是 u≈1–3px 的噪点**，
   把候选数组占满，扫到真符号时已无槽位，被静默丢弃。加 `MIN_MODULE_PX=2.5` 后，
   真定位图形立刻以 u≈20.5px、票数 27–30 排在最前。
2. **四角认领规则错误**。原按「离图像四角最近」认领，被浏览器界面图标骗走——
   实测检出的四点构成上下边 2955px、左右边仅 233px 的极扁矩形。改为几何约束筛选
   （四边近似相等 + 对角线近似相等 + 边长/模块比落在合法档位范围）。
3. **符号朝向未处理**（「头部校验失败」的真凶）。见 `vd_dense_core.c` 中
   `ORIENT_PERM` 的注释。横拍或设备旋转会让符号相对图像转 90°；此时定位全对、
   单应性尺度全对，只是行列被转置。**而规约 3.1 早就规定了右下角定位图形的
   3×3 芯为红色（v=4）专供方向消歧，JS 编码器与 Python 参考实现都写了，
   只有 C 解码器没读它**——先按逐个试探修好，后来才补上 `orient_from_red_core`
   直读。教训：解码端漏实现规约里已有的字段，症状和「格式缺功能」一模一样，
   排查时要先回头对规约。
4. **`refine_edges` 会产生负收益**。它逐段独立测量、段间没有平滑约束，透视较强时
   各段各自撞到 ±2 格的搜索边界，拼出锯齿状的假边。实测有照片因此从
   「纯单应边框环 448/448 全对」被打坏到 342/448。现加 `refine_edges_guarded`：
   校正前后各算一次整圈吻合度，变差就退回纯单应。
5. **RS 伪成功**（最危险的一个）。擦除数逼近 32 时，纠错末尾那道「重算综合征」
   的复验会失效——32 个擦除位置配 32 个校验符号，方程组恰定，无论真实错误在哪
   都必然解出一个合法码字。N=128 照片实测 22 个块全部「纠错成功」，重组出的
   L2 帧却 magic、T、m 各错一位，两张不同照片解出的 CRC 字段还完全相同。
   现加 `RS_ERAS_MAX = RS_PARITY - 8`，留 8 个校验符号不参与求解。
   修完这条，N=128 从「报成功但给垃圾」变成「诚实地报 RS 失败」，
   真实误码率才第一次露出来。
6. **三通道独立阈值判不了八色**（N=128 解不出的真因）。见 `PAL_MIN_SEP` 上方注释：
   屏幕绿基色在相机 R 通道上有强串扰，绿/青两色的 R 读数是 114–118 而非 ~20，
   R 通道因此是**三峰**分布。二均值只能切一刀，中簇落哪边全看样本量——
   N=96 切出阈值 150（侥幸正确），N=128 切出 107（绿格青格的 R 位整类错，
   2/8 的颜色报废）。改用定标条实测调色板做三维最近邻，串扰被直接测进参考值。

**量化过程**（关键在于分离「定位」与「采样」两件事）：

| 观测 | 数值 | 说明 |
|---|---|---|
| Python 直线采样边框环 | 95–97% | 四角与格距本身是对的 |
| C 侧纯单应边框环 | 448/448（相位取反） | 相位取反 = 符号转了 90° |
| C 侧经 refine_edges | ~50% | 校正被相位错配误导，整体崩掉 |
| 朝向修好后 N=96 | 2460B，L2 CRC 通过 | 两张照片同 sessionId、不同 baseBlockId |
| 朝向修好后 N=128 | 4900B 但 L2 CRC 不过 | 顺藤摸到第 5、6 个 bug |
| 阈值判决 N=128 | 边框环 448/448 全对，RS 0/22 | 环只有纯黑纯白，碰不到中簇 |
| 调色板判决 N=128 | RS 22/22，最好的一张纠错 0 次 | 串扰被测进参考值 |

「边框环 100%」这类读数要留神：补零区是一大片纯黑、边框环与定标条又都是专门
标定过的位置，光看命中率会**高估**几何正确性。相位取反才是那条真信息。

**此前「边缘外推模型不够用、必须加内部校正图形」的结论是错的**，
误判来自朝向未对齐时的 RS 通过率（9/22，穷举天花板 18/22）——参数扫描是在
一个转置了的网格上做的，天花板自然上不去。内部校正图形仍然值得做，
但属于优化项而非阻塞项。

同样要留神的是「RS 解码成功」这个信号本身：在第 5 个 bug 修掉之前，
它对 N=128 一直是假的。判定真机是否解出，唯一可信的判据是 **L2 CRC**。

耗时拆分（12MP 静态照片，`-O2`，单线程）：

| 阶段 | 耗时 |
|---|---|
| `find_finders`（全图扫描，与图像像素数成正比） | 18.9 ms |
| 单次 `probe_grid`（与格数相关，与图像大小无关） | 0.62 ms |
| 冷启动合计 | 26.3 ms |

红芯直读朝向把探测次数从「四朝向 × 五档位」降到「一朝向 × 五档位」，
探测部分 12.4 ms → 3.1 ms。冷启动总时间只降到 26 ms，是因为 12MP 静图上
`find_finders` 占了大头；相机帧是 1080p 量级，全图扫描按像素数缩到约 3 ms，
冷启动实际在 6 ms 上下。

调试方法上最有用的一条：**「边框环命中率」对色彩判决完全没有诊断力**。
边框环只有纯黑纯白，是八色里最容易的两个；串扰把中间四色全判错时，
边框环照样 448/448。要看色彩判决，得直接读定标条的八色实测值。

**定标条的八色实测值同样会骗人**，理由和边框环是同一个：定标条在每一帧里
内容都一样。真机诊断包里六张失败帧的调色板八色最小间距 92～114（阈值 40），
几何、每格像素、弓曲全部正常，判决却大面积崩掉。真正有诊断力的是
**数据格的八色分布**——载荷是 RS 编码后的字节流，八色应各占 12.5%；
能解出的帧实测 12.2%～13.1%，崩掉的帧黑色只剩 3.6%、白色高达 25.9%。
分布一偏，判决就废了，而在此之前所有几何与调色板读数都是绿的。

## 几何校正（镜头畸变）

四角单应性只能表达平面投影，**表达不了镜头径向畸变**——实测中等桶形畸变下
96 格符号整帧解不出。当前做法：用边框环的已知交替图案沿四条边分段测量法向
偏移，再按 `shape(u)=β·u+(1−β)·u³` 插值到内部，β 由判决置信度搜索确定
（仅建锁首帧做一次，之后随跟踪锁复用）。

三次失败的建模尝试记录在 `vd_dense_core.c` 的注释里（线性 Coons、纯三次、
显式径向拟合），避免后来者重蹈。

**这是对格式缺陷的补偿，不是正解。** 成熟方案（QR）的答案是在符号内部放
校正图形（alignment pattern），让解码器直接测量内部网格而非从边缘外推。
VD-D1 目前内部没有任何参考点，后续应补上——见仓库根 README 待办。

补偿手段本身也会反噬：`refine_edges` 逐段独立测量、段间无平滑约束，
透视较强时各段撞上 ±2 格搜索边界拼出锯齿假边，真机上把一张原本 100% 正确的
纯单应打坏到 76%。故外包一层 `refine_edges_guarded`，按整圈边框环吻合度
校正前后取优——桶形畸变的图像照旧受益，打坏的原样退回。

## 摩尔纹

屏幕像素栅格与传感器栅格拍频产生的高频分量，单点采样会直接混叠进判决。
`sample_cell` 按每格像素数自适应做 k×k 面积平均（格内侧 60%），即低通滤波。

## 判决偏移校正与屏幕换帧过渡帧

真机一轮 211 帧的诊断包里 56 帧纠错失败（26.5%）。逐帧复现后分成两类：

**一类是判决整体偏移**（4/10 张留样）。定标条读数正常但数据格的八色分布
偏向亮端。`vdd_decode_diag` 现在采样与判决分两遍，中间用「八色等概率」这个
先验算一次整体偏移：所有数据格的三通道均值应当等于同位置调色板八色的均值，
两者之差即为偏移，判决前减掉。效果（都是纠正字节数，越小越好）：

| 样本 | 校正前 | 校正后 |
|---|---|---|
| 真机 128 格 1 / 2 | 206 / 203 | 116 / 119 |
| 真机 128 格 3 / 4 | 1 / 3 | 0 / 0 |
| 诊断包 fail01 | 8/13 块，整帧失败 | 13/13 块，整帧解出 |
| 诊断包 fail09 | 6/13 块 | 12/13 块 |

金图像 8 张、真机老照片 6 张无一退步。

**另一类是屏幕换帧过渡帧**（6/10 张留样），物理上不可解。LCD 从上一帧过渡到
当前帧期间被抓拍，格值是新旧两帧的混合，格间对比整体塌陷——41%～48% 的字节
含低置信格，而能解出的帧只有 8%～11%，两者之间没有交叠。这类帧的定标条读数
完全正常，因为定标条在每一帧里内容相同，混合后不变；崩掉的只有数据区。
上下方向还能看到单调梯度（顶部黑格 2.4%、底部 6.3%），与 LCD 逐行刷新吻合。

25% 已经远超 RS 的物理上限，故打包完位流后先数一遍字节级擦除标记，超过
`stream_len/4` 直接返回 `VDD_ERR_RS`，省掉 13 个块两轮纠错（Mac 上单帧
7～8 ms 降到 6.3 ms）。这只是省 CPU，不会多解出任何一帧——**这类帧要在
采集侧解决**：诊断包里失败多为孤立单帧（35 次长度为 1 的游程，最长 4），
符合「随机落在过渡期」而非「一段时间失焦」。当前相机实际送检 17.3 fps、
屏幕 10 fps，每个屏幕帧只被采样 2.17 次，落空概率高；提高送检帧率比
调解码器更直接。

## 分阶段耗时（诊断模式）

`vdd_diag` 逐帧回填七段耗时，其中前六段互不重叠、加起来约等于整帧：
`find -> probe -> beta -> sample -> decide -> rs`；`ms_geom` / `ms_calib`
是 probe 内部的细分，与 probe 重叠，别重复计入。失败帧同样回填，走到哪算到哪。

真机 N=112 一轮 623 帧的实测中位数（`decode_ms` 59.5 ms，送检 13.8 fps，
成功率 86%）：定位 21.0 ms、采样 23.3 ms 是两个大头，判别 5.4、判决 4.8、
纠错 2.5。**送检帧率就等于 1/decode_ms**——解码是瓶颈，不是在等下一个屏幕帧。

4K（3840×2160、N=128、全图搜索，Mac `-O2`）实测：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 定位 `find_finders` + 局部阈值 | 11.2 ms | 约 60% |
| 档位与朝向判别 | 2.8 ms | |
| β 标定（仅建锁首帧） | 9.4 ms | |
| 逐格采样 | 2.9 ms | |
| 判决 | 0.9 ms | |
| RS 纠错 | 0.1–1.5 ms | |

同一份代码在 1080p 金图像上定位只要 1.1 ms——**定位耗时与像素数成正比，
是高分辨率下的唯一大头**。建锁首帧还要再付 9.4 ms 的 β 标定（跟踪态复用，
不重复付）。要压 4K 的功耗，该动的是这两处，而不是采样或纠错。

遥测 CSV 同时记录 `latency_ms`（采集时间戳到进解码队列）与 `queue_ms`
（解码完成到主 actor 执行）。三个时间分开才说明问题：`latency_ms` 大是采集
管线或队列积压，`decode_ms` 大才是解码本身慢，`queue_ms` 大说明主 actor 忙。

资源占用按秒采样记进同一张表：`cpu_pct`（本进程所有线程合计，可超 100）、
`mem_mb`（phys_footprint，与 Xcode 内存表同源）、`thermal`
（`ProcessInfo.ThermalState`）。**GPU 没记**——公开 API 读不到进程级 GPU
占用，而这条管线本来也不走 GPU（YUV→BGRA 由 ISP 做，其余全在 CPU）。
与其编一个数，不如记热状态：系统按它降频，它一跳到 serious 就解释了帧率下滑。

## 丢锁的代价，以及为什么「静止 20 fps、一播放掉到 5 fps」

真机 15 Pro Max、2K、N=112：对着**静止**的一帧能稳定 20 fps；发送端一开始
播放就掉到 5～12 fps。掉的不是解码——同一个符号解一次和解另一个符号一次
成本一样。差别在**失败帧的连锁反应**：

播放时会出现换帧过渡帧与信噪比不足的帧，纠错失败。当时的处置是丢锁重试，
而丢锁会连带触发全图搜索（4K 实测 65 ms）与 `refine_beta` 重算（56 ms），
遥测里全图搜索帧的 `decode_ms` 中位数 172.8 ms，是跟踪态 58.7 ms 的三倍。
更糟的是重试若也失败，锁就一直是丢的，**之后每一帧都得重新付一次**，
直到某一帧侥幸解出。一两个坏帧就能把帧率按住好几百毫秒。

现在纠错失败只把搜索窗放大（`vdd_lock.wide`），不丢锁：角点重新测一遍，
β 与档位照旧复用。真正丢锁只发生在四个定位图形都找不到的时候。

**教训**：跟踪态的每一项复用（角点、β、档位、朝向）都要分别问「这次失败真的
需要放弃它吗」。把它们捆成一个 valid 位一起丢，代价是隐性的，而且只在
「失败率不为零」的真实场景里才暴露——对着静止画面测永远看不到。

## 跟踪窗为什么要两档

真机遥测里最反直觉的一条：**跟踪态的定位耗时中位数 20.7 ms，只比全图搜索的
64.8 ms 少三倍**——「跟踪」几乎没省下东西。原因是窗口宽度写成了
`max(w,h)/10 + 16`，那是**图像尺寸的固定比例**：1080p 下 208 px 尚可，
4K 下就成了 400 px，四个 800×800 的窗合计 2.56 M 像素，占满帧的 31%。

窗口也不能一味调小，手一晃符号就移出小窗，丢锁的代价是一次全图搜索。
现在先试 `/60` 的小窗，找不齐四个再退回 `/10` 的大窗，都不行才丢锁。
命中时省掉 90% 以上的扫描量（4K 实测定位 11.3 ms -> 1.8 ms，整帧 17 ms -> 4.5 ms），
落空时只多付一次小窗扫描。

定位内部的耗时构成：**游程扫描约 82%、局部阈值约 18%**，所以要继续压定位，
该动的是扫描的像素数，不是阈值的算法。

局部阈值表也只在真正会被扫描的地方建。`scan_rows` 在跟踪态只跑四角的窗，
而 `lt_build` 原本按整幅图算——4K 全图是 207 万次采样（本身已隔行隔列），
四个大窗加起来才几十万像素。按大窗（不是小窗）取，两档重试才都有阈值可用；
窗外的块走原有的「纯色块继承」路径，分块索引不变，`px_dark` 一个字都不用改。
跟踪态定位 1.8 ms -> 0.68 ms，整帧 4.5 ms -> 3.3 ms，三个诊断包逐帧
RS 通过数与改前**逐块相同**。

## 试过但退回的优化

**全图搜索按图像高度放大行步长。** `scan_rows` 固定隔两行扫一次；4K 下定位
图形的环有约 90 px 高，直觉上步长放到 4 也绰绰有余，全图搜索能省一半。实测
把两张原本 22/22 整帧解出的 12MP 实拍打成 0/22。原因是定位图形的中心按命中
行的质心估计，行数减半质心精度也减半，角点一偏后面全盘皆输。这条路走不通，
除非先把角点估计换成不依赖采样密度的做法。

## 相机管线

`DenseCameraScanner` 与 QR 路径的 `CameraScanner` 完全独立，三点关键差异：

1. **BGRA 而非 YUV**：多电平判决要读三通道，YUV→BGRA 由 ISP 硬件完成；
2. **锁定 AE / AWB，对焦始终自动**：连续解出 3 帧后锁死曝光与白平衡。
   屏摄拍的是静止屏幕，多电平判决最大的敌人是相机自动调节造成的光度漂移。
   **但对焦不能一起锁**——早先这里连 `focusMode` 也置成 `.locked`，
   于是解出 3 帧后焦距冻住，手持稍一前后移动就再也解不出，
   表现为「只能在某个固定距离识别」。清晰度归对焦、光度归曝光，必须分开。
   连续失败约 1 秒会自动放开曝光锁，重新自动调节。
   锁定时顺带把快门压到 1/120 s 以内并提 ISO 补偿：手持抖动的运动模糊比噪声
   更致命，而调色板判决对整体明暗免疫（参考色与数据格在同一帧里一起变暗），
   宁可欠曝也要短曝光。对焦另加近距搜索范围限制与中心对焦点，合焦快得多；
3. **无 ML 推理**，不需要 QR 路径那种为保护 Vision 而设的送检帧率上限；
   串行解码队列 + `alwaysDiscardsLateVideoFrames` 天然实现忙时丢帧。
