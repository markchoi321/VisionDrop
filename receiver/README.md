# VisionDrop 接收端

iOS 端文件接收器：摄像头连续扫描发送端滚动播放的密集 8 色色块码（VD-D1）序列，
按喷泉码重组出原始二进制文件。

识别管线与解码核心见 [VisionDrop/DenseL1/README.md](VisionDrop/DenseL1/README.md)，
协议语义见 [../protocol/CONTRACT.md](../protocol/CONTRACT.md)。本文件只讲**采集侧的参数选择**。

## 扫描设置

主界面提供分辨率选择（`720p` / `1080p`），在按下"摄像头扫描"之前生效。
分辨率越高单帧处理越重，先用 720p 试，格子看不清再上 1080p。

相机采集帧率上限 60fps（各分辨率挑支持 60fps 的 `activeFormat`，挑不到取该格式最高帧率），
密集管线逐帧处理，不做限频——C 核心 `-O2` 下 N=128 金图像单帧约 3.3 ms，
远低于 60fps 的 16.7 ms 预算。早先「解码慢、限 20fps」的结论来自 `-O0` Debug 构建
（同一图像 19.3 ms），是假象。

相机在画面稳定后锁定 AE / AWB / 对焦：多电平色彩判决最怕的就是自动调节带来的光度漂移。

## 扫描帧率 vs 发送端显示间隔

接收端的扫描帧率与发送端的符号显示间隔之间存在 **采样混叠（aliasing）** 关系，
是决定成功率的核心因素。这套模型与物理层无关，对色块码同样成立。

### 模型

- 显示间隔 `D`（ms）= 发送端每个符号停留的时间
- 扫描间隔 `S = 1000/fps`（ms）
- 每个符号的期望扫描次数 `N = D / S = D × fps / 1000`

当 `D` 不是 `S` 的整数倍时，每个符号实际拿到的扫描次数会在 `floor(N)` 和 `ceil(N)` 之间
交替（拍频效应）。只命中 1 次的符号里，如果那一次正好落在屏幕刷新过渡瞬间
（相机曝光跨越两个符号），就会得到混合图像而解码失败。

### 每个符号的期望扫描次数表

| 显示间隔 `D` | fps=15 | fps=20 | fps=25 | fps=30 | fps=60 |
|--------------|--------|--------|--------|--------|--------|
| 100 ms       | 1.5    | 2.0    | 2.5    | 3.0    | 6.0    |
| 84 ms        | 1.26   | 1.68   | 2.1    | 2.5    | 5.0    |
| 75 ms        | 1.1    | 1.5    | 1.9    | 2.25   | 4.5    |
| 50 ms        | 0.75   | 1.0    | 1.25   | 1.5    | 3.0    |
| 42 ms        | 0.63   | 0.84   | 1.05   | 1.26   | 2.5    |

### 推荐配置

经验法则：要保证每个符号在扣除过渡帧损失后还有至少 2 次干净的扫描机会，需要
`N = D × fps / 1000 ≥ 2.5`。据此推出发送端的显示间隔下限：

| 扫描帧率 | 显示间隔下限 | 备注 |
|---|---|---|
| 30 fps | 84 ms | `sessionPreset` 隐含的默认上限 |
| 60 fps | 42 ms | 需显式选择支持高帧率的 `activeFormat` |

扫描帧率上限 60fps。超过 30fps 必须显式设置 `activeFormat`——只设 `sessionPreset`
会被隐含钉在 30fps。

**当前推荐：接收端 60fps，发送端 50 ms（60Hz 屏上 3 个刷新周期，N=3）。**
曝光锁定后相机按固定周期采样，与发送端的比值落在整数 3 上，相位基本不漂（见下文）；
但过渡带（卷帘读出 + 1/250 s 曝光）最多污染 2 帧，任何相位下每个符号仍至少剩
1 个干净帧。不要用 33 ms（2 周期）：锁相时可能整符号全废。
旧遥测（20fps、83 ms，N≈1.67）稳定呈 `ooowwooowwooo`，每个符号恰好只拿到一个
干净帧，正是采集时间轴不够密的表现。

### 两个隐性影响

1. **过渡帧损失**：跨越显示切换瞬间的那一帧会把两个符号叠加在一起。曝光锁定时
   快门被压到 1/250 s 以内（ISO 按比例补偿，超上限接受欠曝），过渡带随之收窄；
   调色板判决对整体变暗免疫。把发送端屏幕亮度调高能进一步缓解。
2. **拍频敲准 / 相位锁定**：当 `D × fps / 1000` 恰好是整数（如 20fps × 100ms = 2.0），
   每个符号的扫描时刻相对其显示窗口的相位是固定的，会形成稳定模式——要么稳定命中、
   要么稳定漏掉。接收端只设 `activeVideoMinFrameDuration`、把 `MaxFrameDuration`
   复位到格式最大值，自动曝光期间帧时长可以浮动、相位会漂；但曝光一旦锁定
   （custom 快门），帧时长实际固定，相位只靠两边晶振偏差缓慢漂移，可视为锁定。
   因此靠**比值**兜底：N ≥ 3 时锁在任何相位都不会整符号全废；N 在 1–2 之间才怕锁相，
   这时非整数比（如 2.5）比整数比更稳。

## 其它要点

- **进度持久化**：以二进制 `.vdpg` 格式自动落盘并在启动时恢复，格式见契约第 11 节。
  多会话可并行维护。
- **Debug 构建慢约 50 倍**：Swift 解码器在 Debug 下的实时消元跟不上扫描速度，
  真机现场标定务必用 Release 构建。C 核心 `vd_dense_core.c` 例外：工程里给它单独加了
  `-O2`（同步文件夹的 `additionalCompilerFlagsByRelativePath`），Debug 下也按优化后的
  速度跑，否则 `-O0` 慢约 6 倍，现场采到的 `decode_ms` 会失真。
- **模拟器可跑全流程回归**：识别管线是零依赖纯 C99，不走 Vision，不受模拟器限制。

## Debug 与 Release 的性能差距

本项目最热的代码是紧密的 `UInt64` 异或循环（喷泉码的消元与回代），正好是
优化器差距最大的那一类：`-Onone` 下每次数组访问都带边界检查、不内联、
ARC 也不消除。同一台机器实测：

| 操作 | Debug | Release | 倍数 |
|---|---|---|---|
| 1 MB 文件回代（K=2098、T=500） | 6026 ms | 25.8 ms | 234× |
| 秩 2000 时单个编码块消元（K=2629、T=460） | 9.4 ms | 0.03 ms | 313× |

一帧携带十来个块，所以 Debug 下秩到 2000 之后每帧要在主 actor 上花约 100 ms，
而帧以 20 fps 到达——积压必然发散。真机遥测里 `queue_ms` 从 0 一路涨到
8350 ms、收齐后又跌回 0，就是这条曲线。

**这个差距已经三次被当成性能 bug 排查**（合并慢、收齐瞬间卡死、传输后半程
界面卡顿），因此 Debug 构建启动时会在日志里直接点明。测性能一律用 Release。

## 线程归属

| 任务 | 归属 | 理由 |
|---|---|---|
| L1 解码（定位/采样/判决/纠错） | `dense.decode` 串行队列 | 与界面无关的纯计算 |
| 失败帧留样落盘 | `dense.dump` 串行队列（utility） | 一张 4K BMP 24 MB，绝不能挡解码 |
| **喷泉码消元** | **每会话一条 `vd.blocks` 串行队列** | 代价随秩线性增长，见下 |
| 合并（回代/解流/校验/写盘） | 同上，与消元共用会话队列 | 两者都独占解码器，真并发就是数据竞争 |
| 进度编码 + 写盘 | `vd.progress.io` 串行队列 | 1 MB 文件编出 1.6 MB |
| 界面状态、统计量 | 主 actor | 只做便宜的合并与渲染 |

**解码器只允许在会话自己的 `workQueue` 上访问**（`ReceiveSession.decoder` 是
private，出入口是 `withDecoderSync` / `ingest` / `snapshotForSave`）。主 actor
要读的完成度、秩、是否已释放走加锁的镜像。

之所以按会话分队列而不是共用一条：正确性只要求「同一个会话的解码器不被并发
访问」。共用一条会让互不相干的会话互相排队，并行跑的测试之间也会互相干扰。

消元为什么必须离开主 actor：代价随秩线性增长，K=2629、T=460 时秩 2000 处单块
Release 0.03 ms、Debug 9.4 ms，而**一帧携带十来个块**、帧以 20 fps 到达。
Debug 下后半程每帧要 100 ms，积压必然发散（遥测里 `queue_ms` 一路涨到 8.3 秒）；
Release 下虽然不发散，但进度读数和「完成」按钮照样会被间歇性按住。
**这不是快慢问题，是归属问题**——界面响应和块消元是两件不相干的事。
